## 二、你要包装的项目：无人机三维态势看板原型

你没有真实 WebGL、Cesium、Three.js 经验，所以不能把 Demo 说成“线上生产项目”。正确策略是把它包装为“为了准备大疆行业软件方向做的技术原型”。

这个说法是诚实的，也能体现主动学习能力：

> 我之前没有完整生产级 Cesium 项目经验，但我知道这个岗位可能会涉及无人机态势、三维地图和实时轨迹，所以我做了一个 Three.js 的无人机三维态势原型。它模拟了无人机航线、实时位置、轨迹、告警和点击拾取。我重点验证的是三维场景如何组织、实时数据如何归并、轨迹如何高频更新以及如何避免频繁重建对象导致卡顿。

### 1. 项目背景怎么讲

项目名可以叫“无人机作业态势可视化原型”或“FlightHub Lite 三维态势 Demo”。

业务背景：

> 这个原型模拟的是无人机巡检或应急调度场景。调度人员需要在一个三维界面里看到多台无人机的位置、航线、任务、电量、延迟和告警。右侧面板展示机群列表和当前设备详情，左侧三维场景展示无人机模型、规划航线和实时轨迹。

用户是谁：

> 用户是无人机调度员、行业客户的作业管理员，或者内部研发验证团队。

解决什么问题：

> 它解决的是“实时态势可见”和“异常设备可定位”的问题。传统列表只能看到状态，不能直观看到无人机在空间中的位置和航线关系；三维态势界面可以让用户快速判断无人机在哪里、是否偏离航线、是否有低电量或高延迟。

### 2. 技术选型怎么讲

Demo 使用 Three.js，而不使用 Cesium。这里要主动说明原因：

> 我用 Three.js 做原型，是因为 Three.js 更轻，适合快速验证三维对象、轨迹线、相机控制、点击拾取和渲染更新。真实 GIS 场景如果需要经纬度、地形、影像图层、3D Tiles、倾斜摄影，我会选 Cesium。这个 Demo 的目标不是替代 Cesium，而是先跑通三维可视化和实时数据链路。

这个回答很关键，因为它避免了“你没用 Cesium 却强行说 Cesium 经验”的风险。

可以补一句：

> Three.js 解决的是通用三维渲染问题；Cesium 解决的是地理空间三维问题。大疆这种无人机场景，地图底座更适合 Cesium，局部三维表达和自定义对象可以借鉴 Three.js/WebGL 的思路。

### 3. 架构怎么讲

这个 Demo 可以按四层讲：

第一层是数据模拟层。真实项目中数据来自 WebSocket，包括无人机 ID、时间戳、经纬度、高度、速度、电量、任务状态和告警。Demo 中用定时模拟数据替代 WebSocket，每帧推进无人机在航线上的位置。

第二层是状态归并层。前端以无人机 ID 为 key，维护每台无人机的最新状态。这样 UI 面板和三维场景都读取同一份状态。真实项目中还要处理乱序、重复、丢包、断线重连和补偿拉取。

第三层是三维渲染层。用 Three.js 创建 Scene、Camera、Renderer、无人机模型、航线 Line、轨迹 Line 和地面网格。无人机位置更新时，只修改已有对象的 position 和轨迹 BufferGeometry，而不是每次重新创建对象。

第四层是交互层。使用 OrbitControls 支持拖拽旋转和缩放，用 Raycaster 做三维拾取。点击无人机时，右侧详情面板同步更新，控制器 target 切到当前无人机。

你可以这样说：

> 我把它拆成数据流、状态层、渲染层和交互层。这样做的好处是 WebSocket 消息不会直接操作 DOM 或三维对象，而是先进入状态层，再由渲染循环统一消费。这样能避免高频消息导致界面抖动和对象频繁重建。

### 4. 技术难点怎么讲

难点一：高频实时数据不能直接驱动重渲染。

> 无人机位置可能每秒推送多次。如果每条消息都立即 setState 或重建三维对象，会造成主线程压力。我的处理思路是把消息先归并到状态层，再由 requestAnimationFrame 按浏览器帧率统一渲染。这样数据频率和渲染频率解耦。

难点二：轨迹不能无限增长。

> 实时轨迹如果一直保留，会导致点越来越多，Buffer 越来越大，最终影响 FPS。Demo 里限制每台无人机最多保留 90 个轨迹点。真实项目里可以按时间窗口、抽稀算法或分段加载处理历史轨迹。

难点三：三维对象不要频繁创建销毁。

> Three.js 中 geometry、material、texture 都是 GPU 相关资源。频繁创建销毁会造成性能波动，忘记 dispose 还会导致内存或显存泄漏。所以 Demo 中航线、轨迹和无人机模型初始化后复用，更新时只改 position、rotation 和 BufferGeometry 的 attribute。

难点四：三维点击不是普通 DOM 点击。

> Canvas 里没有 DOM 元素。点击无人机需要把鼠标屏幕坐标转换成标准设备坐标，再用 Raycaster 从相机发射射线，判断射线和三维对象是否相交。命中后再通过对象的 userData 找到无人机 ID。

难点五：真实项目要处理地理坐标。

> Demo 用的是局部坐标，比如 x、y、z。真实无人机数据通常是经纬度和高度。上生产时要把 WGS84 经纬度转换到 Cesium 的 Cartesian3，或者在局部三维场景中做坐标投影和原点偏移。国内地图还要注意 GCJ-02 和 WGS84 的偏移问题。

### 5. 如果被追问“这个项目有什么不足”

你要主动承认边界：

> 这个 Demo 是原型，不是生产级项目。它没有接真实 WebSocket，没有真实地图瓦片，没有做权限、任务下发、断线重连和异常补偿。生产版本我会补充消息协议、设备状态机、接口鉴权、地图坐标转换、轨迹抽稀、监控埋点和资源销毁策略。

这个回答比强行吹项目更可信。

## 三、从零理解 WebGL

你完全没有 WebGL 概念时，可以先把它理解成：浏览器里直接使用 GPU 画图的能力。

普通 HTML/CSS 适合画按钮、表格、文本和布局。Canvas 2D 适合画平面图形。WebGL 适合画大量点、线、面、模型和三维场景。Cesium 和 Three.js 底层都依赖 WebGL，只是它们帮你封装了很多难用的底层 API。

### 1. 为什么需要 WebGL

假设页面上有 10 个图标，用 DOM 渲染完全没问题。假设地图上有 1 万个点位，每个点都是一个 DOM 节点，浏览器需要管理 1 万个元素的布局、样式、事件和绘制，很快就会卡。WebGL 的思路是把点位数据交给 GPU，让 GPU 批量并行绘制。

面试里可以这样讲：

> DOM 适合结构化 UI，但不适合大规模图形对象。地图点位、轨迹、三维模型这类场景更适合 Canvas 或 WebGL，因为它们可以绕开大量 DOM 布局成本，把重复的图形计算交给 GPU。

### 2. WebGL 渲染管线怎么理解

不要背复杂图形学，可以用这条线理解：

```text
JavaScript 准备数据 -> 顶点着色器处理位置 -> 图元装配 -> 光栅化 -> 片元着色器计算颜色 -> 深度测试/混合 -> 显示到屏幕
```

JavaScript 负责准备顶点、颜色、纹理、矩阵等数据。顶点着色器负责处理每个顶点的位置，比如把模型坐标转换成屏幕上能显示的位置。片元着色器负责计算每个像素的颜色。深度测试决定哪个物体挡住哪个物体。

你只需要掌握这个级别：

> 顶点着色器解决“画在哪里”，片元着色器解决“画成什么颜色”。Three.js 和 Cesium 帮我们封装了 shader、buffer、矩阵等底层细节，但性能问题最终仍然和顶点数量、draw call、纹理大小、材质复杂度、每帧更新量有关。

### 3. draw call 是什么

draw call 可以理解为 CPU 命令 GPU 画一次。对象越碎、材质越多、状态切换越多，draw call 往往越多。draw call 太多会导致 CPU 和 GPU 通信成本上升。Three.js 中可以用 `renderer.info.render.calls` 查看当前帧的 draw call 数量。

优化方向：

1. 合并几何体。
2. 复用材质。
3. 使用 InstancedMesh 绘制大量相同对象。
4. 减少透明材质和复杂 shader。
5. 不可见对象不要渲染。

面试说法：

> 如果有大量相同无人机图标或点位，我不会给每个点创建独立复杂对象，而会考虑实例化渲染、合并 geometry 或用 Cesium Primitive 批量绘制，目标是减少 draw call 和对象管理成本。

## 四、从零理解 Three.js

Three.js 是 WebGL 的高级封装。你不用直接写 shader 和 buffer，也能创建三维场景。

一个 Three.js 应用最小模型是：

```text
Scene + Camera + Renderer + Mesh
```

Scene 是三维世界，所有物体都放在里面。Camera 是观察者，决定从哪里看。Renderer 是渲染器，把场景画到 canvas。Mesh 是一个可见物体，由 Geometry 和 Material 组成。

### 1. Geometry 和 Material

Geometry 描述“形状”。比如盒子、球、线、模型顶点。

Material 描述“外观”。比如颜色、金属感、粗糙度、透明度、纹理、是否受光照影响。

Mesh = Geometry + Material。比如一个无人机机身，可以用 BoxGeometry 做形状，用 MeshStandardMaterial 设置颜色和光照效果。

### 2. Camera

常用相机有 PerspectiveCamera 和 OrthographicCamera。

PerspectiveCamera 是透视相机，近大远小，适合三维场景。OrthographicCamera 是正交相机，没有近大远小，适合 CAD、地图俯视、工程图。

Demo 中使用 PerspectiveCamera，因为要展示三维空间感。

### 3. OrbitControls

OrbitControls 是 Three.js 示例库里的相机控制器，可以拖拽旋转、滚轮缩放、平移。它不属于核心渲染能力，但非常适合 Demo 和三维管理平台。

真实项目中，控制器要受业务约束，比如不能钻到地下、不能无限远、点击设备后平滑飞过去、切换俯视/跟随视角。

### 4. Raycaster

Raycaster 用于三维拾取。它解决的问题是：用户点击 canvas 上的某个位置，如何知道点到了哪个三维对象？

流程是：

1. 获取鼠标在 canvas 中的位置。
2. 转成标准设备坐标，范围是 -1 到 1。
3. 从相机位置向这个方向发射一条射线。
4. 判断射线和场景中的对象有没有相交。
5. 取最近的相交对象，读取 userData 中的业务 ID。

面试说法：

> 三维场景点击不是 DOM 事件冒泡，而是射线检测。为了把渲染对象和业务数据关联起来，我会在对象的 userData 上挂 droneId，命中对象后再回到状态层查设备详情。

### 5. Three.js 性能注意点

Three.js 最大的坑之一是资源生命周期。你创建的 geometry、material、texture 很多都在 GPU 侧占资源。如果组件卸载或对象删除时不 dispose，可能造成显存泄漏。

生产实践要注意：

1. 初始化后复用 geometry 和 material。
2. 高频更新只改 attribute、position、rotation，不重建对象。
3. 删除对象时调用 geometry.dispose、material.dispose、texture.dispose。
4. 控制模型面数和纹理大小。
5. 大量相同对象用 InstancedMesh。
6. 长时间运行的页面要观察内存曲线和 FPS。

## 五、从零理解 Cesium

Cesium 可以理解成“专门做三维地球和 GIS 的 WebGL 框架”。如果 Three.js 是通用三维引擎，Cesium 就是地图和地理空间方向的三维平台。

### 1. Cesium 解决什么问题

无人机业务通常不是在一个抽象三维空间里飞，而是在真实地球上飞。真实业务会涉及：

1. 经纬度。
2. 高程。
3. 地形。
4. 卫星影像或地图瓦片。
5. 3D Tiles 城市模型。
6. 航线和禁飞区。
7. 测距、测面、区域标注。
8. 轨迹回放。

这些能力用 Three.js 从零做会非常重，Cesium 已经提供了地球、坐标、影像、地形、相机、图层、实体等能力。

### 2. Viewer、Entity、Primitive

Viewer 是 Cesium 的应用入口。它创建三维地球、场景、相机、图层、时间轴等。

Entity 是上层业务对象抽象。你可以用 Entity 表示无人机点位、航线 polyline、禁飞区 polygon、标签 label。优点是开发简单，和业务模型接近。

Primitive 更底层，更接近渲染对象。它适合大量数据、高性能、自定义材质或批量绘制。缺点是开发复杂。

面试回答：

> 如果是几十到几百个业务对象，我会优先用 Entity，因为开发效率高、代码可读性好。如果是上万点位、复杂轨迹或需要自定义渲染性能，我会考虑 Primitive 或批量渲染。核心取舍是开发效率和渲染性能。

### 3. 3D Tiles

3D Tiles 是 Cesium 生态中用于大规模三维数据的格式，比如倾斜摄影、城市建筑、BIM 模型。它的核心思想是分块和分层加载。离相机远的地方加载低精度数据，近的地方加载高精度数据。

面试说法：

> 3D Tiles 类似三维世界里的瓦片地图。它不是一次性把整个城市模型加载进来，而是按视角和距离逐步加载，这样才能支撑大规模三维场景。

### 4. 坐标问题

无人机上报通常是经纬度和高度。Cesium 使用 WGS84 椭球模型，并提供从经纬度到 Cartesian3 的转换。

你要知道几个词：

WGS84：GPS 常用坐标系。

GCJ-02：国内地图常见加密偏移坐标系。

EPSG:4326 vs EPSG:3857：4326 是经纬度坐标（WGS84），3857 是 Web 墨卡托投影（地图瓦片常用）。前端做地图开发时，接口返回的坐标可能是 4326，但底图瓦片可能是 3857，混用会导致位置偏移。

Cartesian3：Cesium 中的三维笛卡尔坐标。

如果位置偏移，常见原因：

1. 数据是 WGS84，但底图是 GCJ-02。
2. 经纬度顺序写反。
3. 高度单位或参考面不一致。
4. 投影转换错误。
5. 后端返回的数据精度不足。

面试说法：

> 地图偏移我会先确认数据源坐标系和底图坐标系是否一致，再检查经纬度顺序、单位、高程基准和转换逻辑。无人机场景不能只看前端渲染，坐标链路要从设备、后端、地图底图一起排查。

## 六、实时轨迹怎么真正讲明白

实时轨迹不是“收到点就画线”这么简单。完整链路要考虑数据、状态、渲染和异常。

### 1. 数据协议

一条无人机遥测消息可以包含：

```json
{
  "droneId": "M30-01",
  "seq": 10241,
  "timestamp": 1780474733014,
  "longitude": 113.94,
  "latitude": 22.53,
  "altitude": 120,
  "speed": 18,
  "heading": 86,
  "battery": 72,
  "status": "flying"
}
```

你要关注 seq 和 timestamp。seq 用来判断乱序和重复，timestamp 用来做轨迹时间轴和延迟计算。

### 2. 前端状态设计

不要把所有消息直接 push 到数组里。更好的结构是：

```js
const droneState = {
  "M30-01": {
    latest: {},
    trail: [],
    lastSeq: 10241,
    connection: "online"
  }
}
```

latest 保存最新状态，用于设备列表和详情。trail 保存轨迹点，用于地图渲染。lastSeq 用来丢弃重复或过期消息。connection 用来展示在线、离线、延迟。

### 3. 渲染频率控制

WebSocket 消息可能不是稳定 60 次每秒。浏览器渲染通常跟随屏幕刷新率，比如 60FPS。不要让每条消息都触发渲染。

更好的设计：

1. WebSocket 收到消息，只更新内存状态。
2. requestAnimationFrame 每帧读取最新状态。
3. 同一帧内批量更新所有无人机。
4. UI 面板低频刷新，比如 500ms 更新一次。

面试说法：

> 我会把消息频率和渲染频率解耦。消息层负责归并数据，渲染层按帧消费最新状态，右侧 DOM 面板再降频更新。这样即使某一秒消息突增，也不会让 DOM 和三维对象被过度更新。

### 4. 轨迹抽稀

如果每秒 10 个点，一台无人机一小时就是 36000 个点。十台就是 36 万点。直接画会越来越卡。

常见策略：

1. 只保留最近 N 分钟轨迹。
2. 只保留最近 N 个点。
3. 点距离太近时不加入轨迹。
4. 用 Douglas-Peucker 等算法抽稀。
5. 历史轨迹按时间段分页加载。

Demo 使用的是“最多保留 90 个点 + 距离太近不追加”的简化策略。

## 七、WebSocket 怎么讲出工程经验

WebSocket 是双向长连接，适合实时位置、任务指令、协同编辑和告警推送。但工程上不是 new WebSocket 就结束。

### 1. 必须具备的能力

心跳：客户端定期发送 ping，服务端回复 pong。如果超时，认为连接异常。

重连：断线后不要立刻疯狂重连，要用指数退避，比如 1s、2s、4s、8s。

鉴权：连接时带 token，token 过期要刷新或重新连接。

消息序号：用 seq 处理乱序、重复和丢包。

补偿拉取：断线期间错过的消息，重连后通过 HTTP 拉取缺失区间。

降级：WebSocket 不可用时，可以降级到轮询或 SSE。

销毁：页面关闭或组件卸载时关闭连接，移除事件监听。

### 2. WebSocket 和轮询怎么选

可以这样回答：

> 低频状态查询用轮询就够了，实现简单，也容易通过 HTTP 缓存和网关治理。无人机实时位置、告警、任务控制和多人协同更适合 WebSocket，因为它需要低延迟和服务端主动推送。但 WebSocket 的复杂度在连接治理，包括心跳、重连、鉴权、消息序号和补偿。

## 八、浏览器性能要讲“排查路径”

面试官问性能优化，不要只说懒加载、防抖、节流。高级前端要讲排查路径。

### 1. 页面慢怎么查

第一步，看是加载慢还是运行慢。

加载慢看 Network、资源体积、首屏接口、缓存、CDN、JS 包大小。运行慢看 Performance、Long Task、FPS、Layout、Paint、内存。

第二步，定位瓶颈。

如果 JS 执行时间长，可能是大数据计算、复杂 diff、同步循环。  
如果 Layout 多，可能是频繁读写 DOM 尺寸导致强制回流。  
如果 Paint 多，可能是大面积重绘、阴影、滤镜、复杂样式。  
如果内存上涨，可能是事件监听、定时器、WebSocket、Three.js 资源未释放。

第三步，做有针对性的优化。

列表多用虚拟滚动。  
图形多用 Canvas/WebGL。  
计算重用 Web Worker。  
组件多减少不必要重渲染。  
首屏慢做代码分割和资源优先级。  
长期运行卡顿查内存泄漏和对象复用。

#### 长列表优化专项

大疆可能有设备列表、告警列表、日志列表等大量数据场景：

- **虚拟滚动**：只渲染可视区域内的 DOM，常见库有 react-virtualized、@tanstack-virtual、vue-virtual-scroller
- **分页 + 滚动触底加载**：适合移动端或无限滚动场景
- **大表格 canvas 渲染**：如 AG Grid 的 SSRM（Server Side Row Model），几万行也不卡
- **列表项 memo 化**：React 用 `React.memo` / `useMemo`，Vue 用 `v-once` 或 `shouldComponentUpdate` 逻辑

面试说法：

> 设备列表如果上千条，我会优先用虚拟滚动控制 DOM 数量。如果表格列多、数据量大，考虑 AG Grid 这类 canvas 渲染方案。同时列表数据和三维场景共享同一份状态，避免重复存储和不一致。

### 2. 三维场景卡顿怎么查

三维场景要看几个方向：

1. FPS 是否下降。
2. draw call 是否过多。
3. 模型面数是否过高。
4. 纹理是否过大。
5. 每帧是否创建新对象。
6. 是否有大量透明对象。
7. 是否没有裁剪不可见对象。
8. 是否存在资源未 dispose。

面试说法：

> 如果地图三维页面卡，我会先用 Performance 看主线程是否有 Long Task，再看是否每帧有大量 JS 计算或对象创建。如果 CPU 不高但 FPS 低，我会怀疑 GPU 压力，比如 draw call、模型面数、透明材质和纹理。优化上会优先减少每帧更新量、复用对象、合并渲染批次和限制轨迹点数量。

## 九、Vue/React 要讲机制，不要背 API

你只需要选自己最熟的框架讲深。另一个框架能讲基本概念即可。

### 1. Vue 响应式怎么讲

Vue 3 用 Proxy 劫持对象。组件渲染时读取响应式数据，会触发依赖收集。数据变化时，会触发依赖更新，组件进入更新队列。Vue 不会每次修改都立即更新 DOM，而是批量异步更新，所以需要 nextTick 在 DOM 更新后执行逻辑。Vue 2 用 `this.$nextTick(cb)` 或 `Vue.nextTick(cb)`，Vue 3 也可以用 `await nextTick()`，原理是微任务/宏任务调度（优先 Promise.then，降级 MutationObserver 或 setTimeout）。

面试说法：

> Vue 的响应式核心是依赖收集和触发更新。读取数据时 track，修改数据时 trigger。组件更新会进入调度队列，批量 flush，避免同一轮事件循环中多次修改导致多次 DOM 更新。

如果问 computed 和 watch：

> computed 适合派生状态，有缓存，依赖不变就不重新计算。watch 适合副作用，比如请求、日志、联动操作。能用 computed 表达的数据关系，不要滥用 watch。

### 2. React Hooks 怎么讲

React 函数组件每次渲染都会重新执行函数。Hooks 的状态由 React 按调用顺序保存，所以 Hooks 不能写在条件语句里。

useEffect 是处理副作用的地方，比如请求、订阅、定时器。依赖数组决定 effect 什么时候重新执行。闭包问题来自 effect 捕获的是某次渲染时的变量值。

面试说法：

> React 的一个常见坑是闭包和依赖数组。如果 effect 里使用了某个状态但没写进依赖，可能拿到旧值；如果依赖写得太多，又可能导致重复订阅或重复请求。所以需要把副作用边界拆清楚，必要时用 ref 保存可变值，用 cleanup 清理订阅。

### 3. 框架和三维库怎么结合

这点很重要。React/Vue 是声明式 UI，Three.js/Cesium 是命令式渲染对象。不要让框架每次状态变化都重建三维场景。

正确思路：

1. 组件挂载时初始化 Viewer/Scene。
2. 用 ref 保存三维实例。
3. 数据变化时调用命令式 API 更新对象。
4. 组件卸载时销毁实例和资源。
5. 高频数据不要直接驱动组件重渲染。

面试说法：

> 我会把三维引擎实例放在组件生命周期里管理，但不会把每个三维对象都变成 Vue/React 的虚拟 DOM。高频位置更新更适合直接更新 Cesium Entity 或 Three.js Object3D，同时控制 DOM 面板的刷新频率。

## 九点五、TypeScript 要讲清楚价值

大疆高级前端岗位几乎必考 TypeScript。不要只说"TS 能做类型检查"，要讲清楚它在大型团队协作中的工程价值。

### 1. 核心概念

**泛型**：函数或类型可以接受类型参数，实现复用。

```ts
function getVal<T>(obj: T, key: keyof T): T[keyof T] {
  return obj[key]
}
```

**常用工具类型**：

| 类型 | 作用 | 示例 |
|------|------|------|
| `Partial<T>` | 所有属性变可选 | 更新接口，只传变化的字段 |
| `Pick<T, K>` | 选取部分属性 | 组件 props 只取需要的字段 |
| `Omit<T, K>` | 排除部分属性 | 排除敏感字段后再传给前端 |
| `Record<K, V>` | 构造键值对类型 | `Record<string, DroneState>` |
| `ReturnType<F>` | 获取函数返回类型 | 推断异步函数返回的 Promise 内部类型 |

**类型守卫**：`is`、`in`、`typeof`、`instanceof`，用于运行时缩小类型范围。

### 2. 面试说法

> TS 的价值不只是类型检查，而是在大型团队协作中，接口契约、状态结构、组件 props 都有类型约束，减少运行时错误。重构时编译器能帮我们找到所有受影响的地方，比人肉 grep 可靠。在三维场景里，比如 Cesium Entity 的 properties 和 Three.js 的 userData，如果不用 TS 约束，很容易传错字段名或类型，运行时才发现。

## 十、前端安全讲真实场景

安全问题要结合企业软件和无人机场景。

XSS：地图标注、任务名称、设备备注、富文本报告都可能来自用户输入。如果直接 innerHTML 渲染，就可能注入脚本。防护是输出转义、富文本白名单、CSP、避免危险 API。

CSRF：如果使用 Cookie 鉴权，攻击者可能诱导用户发起操作。防护是 SameSite、CSRF Token、Origin/Referer 校验。关键操作必须服务端校验。

权限：前端可以控制菜单、按钮和路由，但不能作为安全边界。比如“返航”“暂停任务”“删除航线”这类操作必须后端校验角色、组织、项目和设备权限。

敏感数据：无人机轨迹、现场图片、视频流、作业区域可能是敏感数据。前端要避免日志泄露、URL 暴露 token、本地缓存残留、下载链接无鉴权。

面试说法：

> 企业行业软件的安全不是只防 XSS。还要考虑组织权限、设备操作权限、审计日志、敏感数据脱敏和私有化部署下的 SSO/OAuth。前端负责体验和第一层防护，关键权限必须服务端兜底。

## 十一、你必须准备的 8 个高频问答

### 1. 你没有 Cesium 经验，怎么胜任？

回答：

> 我没有把自己包装成生产级 Cesium 经验。但我已经补了 WebGL、Three.js 和 Cesium 的基础差异，并做了一个 Three.js 的无人机态势原型，把三维对象、航线、轨迹、拾取和实时状态归并跑通。Cesium 的学习重点我也明确了：Viewer、Entity、Primitive、3D Tiles、坐标转换和图层管理。我认为上手真实业务时，难点不只是 API，而是实时数据、性能、状态管理和工程化，这部分和我已有前端经验是能迁移的。

### 2. Three.js 和 Cesium 区别是什么？

回答：

> Three.js 是通用三维渲染库，适合自定义三维场景、模型展示和 WebGL 效果。Cesium 是地理空间三维平台，适合三维地球、经纬度、影像图层、地形、3D Tiles 和 GIS 场景。无人机行业软件如果要基于真实地理位置展示航线和设备，Cesium 更合适；如果是局部三维模型或自定义效果，Three.js 更灵活。

### 3. 实时轨迹怎么实现？

回答：

> 后端通过 WebSocket 推送无人机遥测数据，消息包含 droneId、seq、timestamp、经纬度、高度、速度、电量等。前端按 droneId 维护最新状态和轨迹数组，用 seq 处理乱序和重复。渲染层不直接由每条消息触发，而是 requestAnimationFrame 按帧消费最新状态。轨迹做点数限制、距离过滤或抽稀，避免长时间运行越来越卡。

### 4. 地图上几千台设备卡顿怎么办？

回答：

> 先定位是 DOM、JS 还是 GPU 瓶颈。几千设备不适合每个都用复杂 DOM。地图上可以用聚合、分层加载、视野裁剪、Primitive 或实例化渲染。低缩放级别显示聚合，高缩放级别显示单设备。右侧列表用虚拟滚动。高频状态先归并再批量渲染，避免每条消息触发 UI 更新。

### 5. WebSocket 断了怎么办？

回答：

> 客户端要有心跳检测，超时后标记连接异常并触发重连。重连采用指数退避，避免服务端雪崩。每条消息带 seq 或 timestamp，重连后通过 HTTP 拉取断线期间缺失的数据。UI 上保留最后状态并提示数据延迟，关键控制操作在连接不稳定时要禁用或要求服务端确认。

### 6. Vue/React 和三维引擎怎么结合？

回答：

> 三维引擎是命令式的，Vue/React 是声明式 UI。我会在组件挂载时初始化 Cesium Viewer 或 Three.js Scene，用 ref 保存实例。业务状态变化时，低频状态可以驱动组件更新，高频位置数据直接更新三维对象。组件卸载时销毁 viewer、geometry、material、事件监听和 WebSocket，避免内存泄漏。

### 7. 你做过什么性能优化？

回答模板：

> 我会先定位瓶颈，而不是直接套优化手段。加载慢看 Network、包体积、缓存和首屏接口；运行卡看 Performance 的 Long Task、FPS、Layout 和 Paint；内存问题看 Memory。针对重型地图场景，我会减少 DOM 数量、限制轨迹点、合并渲染更新、用 Worker 处理计算、复用三维对象，并通过指标验证优化效果。

### 8. 如何排查线上白屏？

回答：

> 先看监控和用户环境，判断是资源加载失败、JS 运行错误、接口阻塞、浏览器兼容还是发布缓存问题。通过 SourceMap 定位堆栈，看最近发布和依赖变更。Network 看 JS/CSS 是否 404 或 MIME 错误。必要时回滚。后续补充白屏检测、资源加载监控、灰度发布和关键链路自动化检查。

### 9. 前端路由 hash 和 history 模式区别？

回答：

> hash 模式用 `#` 号，不会触发页面刷新，兼容性好，部署时不需要服务端配合。history 模式用 `pushState`，URL 更干净，没有 `#`，但需要服务端配置 fallback，否则刷新会 404。企业内部系统通常 history 模式配合 Nginx 的 `try_files` 配置。Vue Router 和 React Router 都支持两种模式。

### 10. 你如何做前端监控？

回答：

> 接入 Sentry 或自建监控，捕获 JS 错误、白屏、接口异常、性能指标（FCP/LCP/FID）。关键操作加埋点，三维场景加 FPS 和内存监控。错误上报带用户、设备、版本、页面上下文。大疆这种长时间运行的行业软件，还要关注内存泄漏和 WebSocket 断线率。监控不只是报错，还要能回放用户操作路径，帮助定位问题。

### 3. 面试中算法题怎么答

> 先和面试官确认题意和边界条件，不要上来就写代码。说清楚思路、时间复杂度和空间复杂度，再开始写。写完后主动走一遍测试用例。如果有 bug，不要慌，顺着代码逐步排查。

## 十五、心态准备

- **不会的就说不会，但要说出你的思考方向**。比如”Cesium 的 3D Tiles 调度我还没深入过，但我知道它的核心是分层分块和屏幕空间误差控制，具体实现细节我入职后会优先补齐”
- **面试官考的不只是”你会什么”，而是”你遇到不会的问题怎么处理”**
- **高级前端的价值在于**：能拆问题、能做取舍、能讲清楚为什么这么做
- **被追问时不要慌**，追问说明面试官对你的回答感兴趣，是好事
- **反问环节不要跳过**，准备 3-5 个问题，展示你对岗位的认真思考
